This is the exact sequence used to bring the lab up; every command below was run for real.

Prerequisites

Everything here is available from stock Ubuntu apt repos except two packages (libboost1.83 and a matching cpprestsdk) needed by one repo whose HTTP client library predates current Boost. Do the rest with apt.

Gotcha — two of the ten repos need an older Boost

rt-mbms-client links a cpprestsdk build that predates Boost 1.90's API changes. On a machine whose only Boost is 1.90+ (any current Ubuntu), its CMake configure fails looking for a matching boost_random component. The fix isn't a code change — it's building Boost 1.83 and cpprestsdk against it, once, into their own prefix.

bash — build once, ~25 min
# Boost 1.83 into its own prefix, kept separate from the system's Boost 1.90
wget -q https://archives.boost.io/release/1.83.0/source/boost_1_83_0.tar.gz
tar xzf boost_1_83_0.tar.gz && cd boost_1_83_0
./bootstrap.sh --prefix=/opt/boost-legacy
sudo ./b2 install --prefix=/opt/boost-legacy -j$(nproc)
cd ..

# cpprestsdk, built against that Boost, installed to the normal /usr/local
git clone --recursive -b v2.10.19 https://github.com/microsoft/cpprestsdk.git
cd cpprestsdk && mkdir build && cd build
cmake .. -DBOOST_ROOT=/opt/boost-legacy -DCMAKE_BUILD_TYPE=Release
make -j$(nproc) && sudo make install

Everything else builds against the system's own Boost 1.90 — this legacy prefix is only ever passed explicitly, in one place (step 02, rt-mbms-client).

Passwordless sudo (optional, for automation)

The EPC and the receive-side network namespace both need root. If you intend to drive any of this from a non-interactive shell (CI, an agent, a script with no TTY), plain sudo won't prompt correctly. Grant your own user NOPASSWD once via sudo visudo, or just run the launch scripts from an interactive terminal — either works.

05

The ZMQ→SDR bridge

This is the one piece that doesn't ship anywhere. rt-mbms-modem only ever opens radios through SoapySDR::Device::make() — there is no code path that skips SoapySDR, even for a software-radio loopback. So the eNB's ZeroMQ transmit output needs a small SoapySDR device plugin sitting in front of the modem, translating one into the other.

What it actually bridges

rt-mbms-tx's eNB uses srsRAN's own native zmq RF driver in tx_type=pub mode: it binds a ZMQ PUB socket and free-runs, broadcasting raw interleaved complex-float32 I/Q bursts (no framing, no header — see _rf_zmq_tx_baseband() in rf_zmq_imp_tx.c) to whoever's listening. This plugin is the "whoever's listening": a SUB socket, drained continuously into a ring buffer from a background thread, mirroring srsRAN's own reference receiver (rf_zmq_imp_rx.c/rf_zmq_async_rx_thread) almost line for line.

SoapyZmqBridge.cpp — save this file verbatim
// Minimal SoapySDR device plugin that bridges to srsenb's ZMQ RF driver
// (srsRAN's native "zmq" device, tx_type=pub -- a ZMQ_PUB socket bound at
// tx_port that free-runs, broadcasting raw interleaved complex-float32 I/Q
// bursts to any connected subscriber; see rf_zmq_imp_tx.c/_rf_zmq_tx_baseband
// and rf_zmq_imp_rx.c/rf_zmq_async_rx_thread in rt-mbms-modem's vendored
// srsRAN tree, which this bridge mirrors on the RX side). This lets
// rt-mbms-modem run in its normal live-SDR mode (no -f file, no restart
// loop) while the "radio" underneath is actually srsenb's live ZMQ TX
// output. No real hardware involved.
//
// device_args:
//   driver=zmqrx
//   rx_port=tcp://127.0.0.1:2000   (srsenb's tx_port; "endpoint" also accepted)
//   base_srate / native_srate: accepted and ignored (informational only --
//     no resampling/decimation is implemented; keep the eNB and modem at the
//     same n_prb / sample rate).

#include <SoapySDR/Device.hpp>
#include <SoapySDR/Registry.hpp>
#include <SoapySDR/Logger.hpp>
#include <zmq.h>
#include <atomic>
#include <chrono>
#include <complex>
#include <condition_variable>
#include <cstdio>
#include <cstring>
#include <mutex>
#include <stdexcept>
#include <thread>
#include <vector>

namespace {
constexpr size_t kRingCapacitySamples = 3072000; // 10 subframes @ 20 MHz
}

class SoapyZmqBridge : public SoapySDR::Device
{
public:
    explicit SoapyZmqBridge(const SoapySDR::Kwargs &args)
        : _ring(kRingCapacitySamples)
    {
        std::string endpoint = "tcp://127.0.0.1:2000";
        auto it = args.find("rx_port");
        if (it == args.end()) it = args.find("endpoint");
        if (it != args.end()) endpoint = it->second;

        _ctx = zmq_ctx_new();
        _sock = zmq_socket(_ctx, ZMQ_SUB);
        zmq_setsockopt(_sock, ZMQ_SUBSCRIBE, "", 0);
        int timeout_ms = 100;
        zmq_setsockopt(_sock, ZMQ_RCVTIMEO, &timeout_ms, sizeof(timeout_ms));
        int rc = zmq_connect(_sock, endpoint.c_str());
        if (rc != 0) {
            SoapySDR::logf(SOAPY_SDR_ERROR, "SoapyZmqBridge: failed to connect to %s", endpoint.c_str());
        } else {
            SoapySDR::logf(SOAPY_SDR_INFO, "SoapyZmqBridge: subscribed to %s", endpoint.c_str());
        }

        _running = true;
        _rxThread = std::thread(&SoapyZmqBridge::rxThreadBody, this);
    }

    ~SoapyZmqBridge() override
    {
        _running = false;
        if (_rxThread.joinable()) _rxThread.join();
        if (_sock) zmq_close(_sock);
        if (_ctx) zmq_ctx_destroy(_ctx);
    }

    std::string getDriverKey(void) const override { return "zmqrx"; }
    std::string getHardwareKey(void) const override { return "ZmqRx"; }

    size_t getNumChannels(const int direction) const override
    {
        return direction == SOAPY_SDR_RX ? 1 : 0;
    }

    std::vector<std::string> listAntennas(const int, const size_t) const override { return {"RX"}; }
    void setAntenna(const int, const size_t, const std::string &) override {}
    std::string getAntenna(const int, const size_t) const override { return "RX"; }

    bool hasGainMode(const int, const size_t) const override { return true; }
    void setGainMode(const int, const size_t, const bool) override {}
    void setGain(const int, const size_t, const double) override {}
    void setGain(const int, const size_t, const std::string &, const double) override {}

    void setFrequency(const int, const size_t, const double freq, const SoapySDR::Kwargs &) override { _freq = freq; }
    double getFrequency(const int, const size_t) const override { return _freq; }

    void setBandwidth(const int, const size_t, const double bw) override { _bw = bw; }
    double getBandwidth(const int, const size_t) const override { return _bw; }

    void setSampleRate(const int, const size_t, const double rate) override { _rate = rate; }
    double getSampleRate(const int, const size_t) const override { return _rate; }
    std::vector<double> listSampleRates(const int, const size_t) const override { return {_rate}; }

    SoapySDR::Stream *setupStream(const int direction, const std::string &format,
                                   const std::vector<size_t> &, const SoapySDR::Kwargs &) override
    {
        if (direction != SOAPY_SDR_RX) return nullptr;
        if (format != "CF32") {
            SoapySDR::logf(SOAPY_SDR_ERROR, "SoapyZmqBridge: only CF32 format supported, got %s", format.c_str());
            return nullptr;
        }
        return reinterpret_cast<SoapySDR::Stream *>(this);
    }

    void closeStream(SoapySDR::Stream *) override {}
    int activateStream(SoapySDR::Stream *, const int, const long long, const size_t) override { return 0; }
    int deactivateStream(SoapySDR::Stream *, const int, const long long) override { return 0; }

    int readStream(SoapySDR::Stream *, void *const *buffs, const size_t numElems,
                    int &flags, long long &timeNs, const long timeoutUs) override
    {
        flags = 0;
        timeNs = 0;
        auto *out = reinterpret_cast<std::complex<float> *>(buffs[0]);

        std::unique_lock<std::mutex> lock(_ring.mutex);
        if (_ring.count == 0) {
            _ring.cv.wait_for(lock, std::chrono::microseconds(timeoutUs > 0 ? timeoutUs : 100000),
                               [this] { return _ring.count > 0 || !_running; });
        }
        size_t take = std::min(_ring.count, numElems);
        for (size_t i = 0; i < take; ++i) {
            out[i] = _ring.buf[_ring.head];
            _ring.head = (_ring.head + 1) % _ring.buf.size();
        }
        _ring.count -= take;
        if (take == 0) return SOAPY_SDR_TIMEOUT;
        return static_cast<int>(take);
    }

private:
    struct Ring {
        explicit Ring(size_t capacity) : buf(capacity) {}
        std::vector<std::complex<float>> buf;
        size_t head = 0, tail = 0, count = 0;
        std::mutex mutex;
        std::condition_variable cv;
    };

    void rxThreadBody()
    {
        std::vector<uint8_t> rxbuf(1 << 20);
        while (_running) {
            int n = zmq_recv(_sock, rxbuf.data(), rxbuf.size(), 0);
            if (n < 0) continue; // EAGAIN on ZMQ_RCVTIMEO expiry is the normal idle case
            if (static_cast<size_t>(n) == rxbuf.size()) {
                rxbuf.resize(rxbuf.size() * 2);
                SoapySDR::logf(SOAPY_SDR_WARNING, "SoapyZmqBridge: grew recv buffer to %zu bytes", rxbuf.size());
            }
            size_t nsamples = static_cast<size_t>(n) / sizeof(std::complex<float>);
            if (nsamples == 0) continue;
            auto *samples = reinterpret_cast<std::complex<float> *>(rxbuf.data());

            std::lock_guard<std::mutex> lock(_ring.mutex);
            for (size_t i = 0; i < nsamples; ++i) {
                if (_ring.count == _ring.buf.size()) {
                    _ring.head = (_ring.head + 1) % _ring.buf.size();
                    --_ring.count;
                }
                _ring.buf[_ring.tail] = samples[i];
                _ring.tail = (_ring.tail + 1) % _ring.buf.size();
                ++_ring.count;
            }
            _ring.cv.notify_one();
        }
    }

    void *_ctx = nullptr;
    void *_sock = nullptr;
    double _freq = 0, _bw = 0, _rate = 15360000.0;
    std::atomic<bool> _running{false};
    std::thread _rxThread;
    Ring _ring;
};

static SoapySDR::KwargsList findZmqBridge(const SoapySDR::Kwargs &)
{
    SoapySDR::Kwargs args;
    args["driver"] = "zmqrx";
    args["label"] = "ZMQ RX Bridge to srsenb";
    return {args};
}

static SoapySDR::Device *makeZmqBridge(const SoapySDR::Kwargs &args) { return new SoapyZmqBridge(args); }

static SoapySDR::Registry registerZmqBridge("zmqrx", &findZmqBridge, &makeZmqBridge, SOAPY_SDR_ABI_VERSION);

Gotcha — duplicate module registration

If SOAPY_SDR_PLUGIN_PATH also points at ~/soapy-zmq-bridge (the receive launcher below sets this by default) and the module is also installed system-wide, SoapySDR logs duplicate entry for zmqrx at startup. It's cosmetic — SoapySDR just picks one and continues — but if it bothers you, only install to one location.

Sanity-check it standalone

Before wiring this into the full stack, confirm the bridge actually receives real bytes. Bind a fake publisher, then read from the bridge directly:

fake_enb_pub.py
import zmq, numpy as np, time
ctx = zmq.Context(); sock = ctx.socket(zmq.PUB); sock.bind("tcp://*:2000")
time.sleep(1.0)
i = 0
while True:
    t = np.arange(15360) + i * 15360
    iq = (np.cos(t * 0.01) + 1j * np.sin(t * 0.01)).astype(np.complex64)
    sock.send(iq.tobytes())
    i += 1
    time.sleep(0.001)

Run it, then use SoapySDRUtil --probe="driver=zmqrx,rx_port=tcp://127.0.0.1:2000" or a short C++ test that calls SoapySDR::Device::make() and readStream() in a loop — you should see non-zero sample counts with values in the expected ±1 range. This step catches a broken bridge before it's buried under three other processes' logs.

Configuration & certificates

rt-mbms-examples' scripts/tmux/mbms-broadcast-tutorial/conf/ ships a complete, working ZeroMQ config set for every component — you shouldn't need to touch the .conf files themselves. Two things still need generating: the BM-SC's mTLS certificate pair, and the portal's xMB client wiring.

Generate the BM-SC's mTLS certificates

bash
cd ~/rt-mbms-examples/scripts/tmux/mbms-broadcast-tutorial
mkdir -p conf/certs && cd conf/certs
openssl req -x509 -newkey rsa:2048 -nodes -keyout server_key.pem \
  -out server_cert.pem -days 3650 -subj "/CN=localhost"
openssl req -x509 -newkey rsa:2048 -nodes -keyout client_key.pem \
  -out client_cert.pem -days 3650 -subj "/CN=xmb-client"

conf/bmsc.conf already points tls_cert_path / tls_key_path / trusted_client_cert_path at exactly these three filenames — nothing else to edit there.

Point the portal at the BM-SC and the certs

Add to ~/rt-mbms-application-provider/.env (left blank in step 04):

.env
PORT=8080
XMB_SERVER_URL=https://127.0.0.1:8543
XMB_CLIENT_CERT_PATH=/home/<you>/rt-mbms-examples/scripts/tmux/mbms-broadcast-tutorial/conf/certs/client_cert.pem
XMB_CLIENT_KEY_PATH=/home/<you>/rt-mbms-examples/scripts/tmux/mbms-broadcast-tutorial/conf/certs/client_key.pem
XMB_INSECURE_SKIP_SERVER_VERIFY=true

The self-signed server cert has no chain to a real CA, so XMB_INSECURE_SKIP_SERVER_VERIFY=true is the honest setting for a local lab — the portal logs a loud warning about it on startup, which is the point.

Gotcha — the handshake that silently never completes

Even with correct certs, the portal's first request to the BM-SC can fail with the BM-SC logging Error: received handshake message out of context. in a tight loop, and the portal returning a generic connection error. The cause: Node negotiates TLS 1.3 by default, and the BM-SC's xMB-C listener (libmicrohttpd over GnuTLS) can't complete a TLS 1.3 handshake at all. This is the same underlying incompatibility the project already works around for outbound HTTPS pulls from modern CDNs (see the content-loading proxy in step 08) — here it's the inbound direction. The fix is one line in rt-mbms-application-provider/lib/xmb-client.js, in the https.Agent constructor:

lib/xmb-client.js
// before
const agent = new https.Agent({ cert, key, ca, rejectUnauthorized, keepAlive: true });

// after -- caps the handshake at TLS 1.2, which GnuTLS on the BM-SC side completes fine
const agent = new https.Agent({ cert, key, ca, rejectUnauthorized, keepAlive: true, maxVersion: 'TLSv1.2' });

If you've already applied this patch and still see the error, you're probably looking at a stale log — restart the portal process and the handshake errors stop appearing for any new requests.

07

Launch the stack

Two scripts, run in order, in ~/rt-mbms-examples/scripts/tmux/mbms-broadcast-tutorial/. The transmit side runs in your normal (root) network namespace; the receive side runs inside its own namespace so its multicast traffic doesn't collide with the eNB's own M1-U receiver on the same host.

  1. Start the transmit side
    bash
    ./transmit.sh

    Prompts for your sudo password once (srsepc needs root for its TUN interface), then launches, in order: EPC, eNB, MBMS-GW, BM-SC, and the portal. Logs land in ~/.local/state/mbms-broadcast-tutorial/<Name>.log.

    Earlier versions of this tutorial also launched a small ul-feeder helper alongside the eNB, to answer its own uplink ZMQ requests with zero-sample bursts (this eNB has no real uplink — nothing else would ever answer them). That's no longer needed: the ZMQ radio driver itself now zero-fills and paces correctly when nothing answers its uplink socket, so there's nothing left for a separate helper process to do.

  2. Start the receive side
    bash
    sudo ./receive-netns.sh start

    Creates network namespace mbms-rx, a veth pair (10.80.0.1 root ↔ 10.80.0.2 namespace), and launches modem, client, and application inside it. The modem's ZMQ RX connects to tcp://10.80.0.1:2000 — the eNB's TX, reachable over the veth.

Gotcha — the TUN-interface race

The modem creates its mbms_modem_tun device only once it's achieved cell sync (PSS/SSS + MIB decode), which can take longer than the script's 20-second wait, especially on a first cold run. If you see WARNING: mbms_modem_tun never appeared, check the modem's log first — if it shows a clean MIB decode and TUN file descriptor N, the interface exists but is simply still DOWN. Bring the rest of the setup up manually:

bash
sudo ip netns exec mbms-rx ip addr add 192.168.180.10/24 dev mbms_modem_tun
sudo ip netns exec mbms-rx ip link set mbms_modem_tun up
sudo ip netns exec mbms-rx ip route replace 224.0.0.0/4 dev mbms_modem_tun
sudo ip netns exec mbms-rx sysctl -q -w net.ipv4.conf.mbms_modem_tun.rp_filter=0
sudo ip netns exec mbms-rx sysctl -q -w net.ipv4.conf.all.rp_filter=0
sudo ip netns exec mbms-rx nft add table ip mbmsfix
sudo ip netns exec mbms-rx nft add chain ip mbmsfix pre \
  '{ type filter hook prerouting priority -300; policy accept; }'
sudo ip netns exec mbms-rx nft add rule ip mbmsfix pre iifname mbms_modem_tun \
  ip saddr 127.0.0.0/8 ip saddr set 192.168.180.1

The last three lines matter beyond the race condition, too: BM-SC and MBMS-GW both run on loopback, so recovered broadcast packets arrive on the TUN with a 127.0.0.1 source — and the kernel silently drops multicast datagrams with a loopback source on a non-loopback interface, before they ever reach a socket. Rewriting the source in prerouting is what makes the announcement channel and the content both actually arrive.

Gotcha — the client can crash on a cold start

If the client process launches before the TUN interface is up, it aborts immediately: terminate called after throwing ... set_option: No such device. If this happens, just restart it once the TUN steps above are done — it binds cleanly the second time.

This is the actual point of the exercise: get a real HLS stream ingested by the BM-SC over xMB, not fed to the middleware directly. The flute-ffmpeg example project supplies test video and the transcoding script; you supply an HTTP server and an xMB session.

Serve it over plain HTTP

The BM-SC's Application/Pull ingestion fetches over libcurl+GnuTLS, which — per the same GnuTLS limitation noted in step 06 — can't complete a TLS 1.3 handshake against modern HTTPS CDNs either. Since this content is already local, skip TLS entirely:

bash
cd ~/rt-mbms-examples/flute-ffmpeg/watchfolder/hls
python3 -m http.server 8899 --bind 127.0.0.1 &
If you're pulling a real HTTPS/CDN source instead

The example repo ships demo-content/hls-http-proxy.js for exactly that case — it does the HTTPS handshake to the origin itself (Node's TLS stack handles 1.3 fine) and re-serves the whole playlist tree to the BM-SC over plain HTTP, rewriting the origin URLs in the manifests so segment requests come back through it too.

Describe the session as an xMB template

An xMB template is just JSON: one service, one or more sessions. The shipped demo-content/rtve-24h.json is a good starting reference; copy it and point applicationEntryPointURL at your own server:

demo-content/my-content.json
{
  "service": {
    "serviceClass": "urn:example:live-tv",
    "serviceNames": ["My local demo"],
    "serviceLanguages": ["eng"],
    "receiveOnlyMode": true,
    "serviceAnnouncementMode": "SACH"
  },
  "sessions": [
    {
      "sessionType": "Application",
      "maxBitrate": 4000000,
      "fecEnabled": false,
      "mbmsBearer": {
        "tmgiMcc": "901", "tmgiMnc": "56",
        "tmgiServiceId": 20,
        "mcastAddr": "239.255.0.1", "port": 2153,
        "tsi": 3, "serviceAreaCode": 1, "cTeid": 2,
        "mmeSmPeers": "127.0.0.1:2123"
      },

        "ingestMode": "Pull",

      }
    }
  ]
}
Keep tsi / cTeid / tmgiServiceId distinct

The ROM SACH (the always-on announcement channel) reserves service_id 0 and its own tsi (see conf/bmsc.conf's [rom_sach] block). The shipped rtve-24h.json example uses tsi: 1. If you plan to run more than one session, or run this alongside the shipped example, give each its own tsi, cTeid, and tmgiServiceId — two sessions sharing any of the three will silently misbehave rather than fail loudly. mcastAddr/port must match mbms-gw.conf's own m1u_multi_addr (239.255.0.1 in the shipped config) — the port (2153) is this tutorial's established M1-U/GTP-U convention.

Load and activate it

bash

# -> service created  id=svc-1

Loading only describes the session — it doesn't broadcast anything yet. Activate it from the portal's xMB tab, or directly:

bash
curl -u admin:<AUTH_TOKEN> -X PUT \
  -H "Content-Type: application/json" -d '{"state":"Active"}' \

Give this call up to a minute: activating makes the BM-SC synchronously construct a real FLUTE transmitter and, for a Pull session, fetch the manifest — fast on a warm cache, considerably slower on the first fetch. A slow response is not the same as a failed one.

09

Verify, then watch

Confirm each hop before assuming the last one is the problem — the chain is long enough that "no video" could mean six different things.

  1. MBMS-GW is forwarding real content, not just the SACH

    tail -f ~/.local/state/mbms-broadcast-tutorial/MBMS-GW.log — small (∼600–1100 byte) packets every few seconds are just the announcement channel; full 1460-byte packets at a high, steady rate on your session's cTeid are the actual video.

  2. The modem is decoding cleanly

    In the modem's log, look for MBMS dedicated cell in the MIB line, and MCH TOTAL ERRORS 0 repeating. Any nonzero error count here means the RF loopback itself has a problem — go back to step 05 before looking further downstream.

  3. The client received the service announcement

    SA file sa.multipart.gzip (TOI N) has been received in the client's log, followed (once your session activates) by Setting delivery type HLS and a live stream of ContentStream: ... has been received lines for your actual segments.

  4. The client's API reports the service
    bash
    curl http://10.80.0.2:3020/client-api/services

    Should return your service with "protocol":"HLS" and a flute_info field matching your template's mcastAddr/port/tsi.

  5. Watch it

    Open http://10.80.0.2:3000 — the player, running inside the receive namespace.

10

Tear down

bash
sudo ~/rt-mbms-examples/scripts/tmux/mbms-broadcast-tutorial/receive-netns.sh stop
~/rt-mbms-examples/scripts/tmux/mbms-broadcast-tutorial/transmit.sh --stop

The receive-side teardown deletes the whole mbms-rx namespace and its veth; the transmit-side stop signals every process it started by name, escalating to SIGKILL after a few seconds, and waits out the EPC's SCTP socket before returning — both are safe to re-run if something was already stopped.
